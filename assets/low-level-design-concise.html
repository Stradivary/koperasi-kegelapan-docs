1. Register Member

Aktor: Admin (Station)
Tujuan: Mendaftarkan anggota baru dan menerbitkan kartu NFC.
Alur: Admin terlebih dahulu membuat data anggota (nama, userId) di sistem → data member disimpan ke IndexedDB + outbox → setelah member terdaftar, admin memilih member tersebut untuk diterbitkan kartunya → mengisi saldo awal dan masa berlaku → sistem generate CardId unik (7 byte random) → membangun CardPayload lengkap (header, identity, wallet, trailer) → payload di-encrypt dengan AES-256-GCM dan ditandatangani HMAC → kartu NFC di-scan → jika kartu kosong langsung tulis, jika sudah terisi muncul dialog konfirmasi overwrite → setelah write berhasil, data kartu disimpan ke IndexedDB (cards table) dan ditambahkan ke reconciliation outbox untuk sync ke server.
Prasyarat: Data anggota harus sudah ada sebelum kartu bisa diterbitkan. 

flowchart LR
    A[Admin Create Member] --> B[Save Member to DB]
    B --> C[Select Member for Card Issuance]
    C --> D[Input: Balance + Expiry]
    D --> E[Generate CardId]
    E --> F[Build CardPayload]
    F --> G[Encrypt + HMAC Sign]
    G --> H[Scan NFC Card]
    H --> I{Card Blank?}
    I -- Yes --> J[Write to Card]
    I -- No --> K{Confirm Overwrite?}
    K -- Yes --> J
    K -- No --> L[Cancel]
    J --> M{Write OK?}
    M -- No --> N[Error]
    M -- Yes --> O[Save Card to IndexedDB]
    O --> P[Outbox + Sync]
    P --> Q[Success]

2. Topup

Aktor: Admin (Station)
Tujuan: Mengisi ulang saldo kartu anggota.
Alur: Admin memilih kartu dari daftar → scan kartu NFC fisik → sistem memverifikasi kartu yang di-scan sesuai dengan yang dipilih → cek status blokir (kartu + user) → admin memasukkan nominal → validasi: minimal Rp 2.000, maksimal Rp 2.000.000, total saldo tidak boleh melebihi Rp 16.000.000 → applyTopup menambah saldo dan increment counter → payload baru disimpan ke write journal sebagai backup → payload di-encrypt ulang dan ditulis ke kartu → jika verifikasi write berhasil, journal entry dihapus dan transaksi dicatat ke outbox dan transaction log.
Write Journal (Retry Strategy): Sebelum write ke kartu, payload baru disimpan ke write journal sebagai backup. Jika verifikasi gagal (kartu dicabut terlalu cepat / write corrupt), journal tetap tersimpan. Pada tap berikutnya, sistem mendeteksi journal pending → otomatis retry write tanpa perlu input ulang dari admin. Setelah retry berhasil dan terverifikasi, journal entry dihapus. 

flowchart LR
    A[Select Card] --> B[Scan NFC]
    B --> C{Card Matches?}
    C -- No --> D[Error: Wrong Card]
    C -- Yes --> E{Blocked?}
    E -- Yes --> F[Error: Blocked]
    E -- No --> G[Input Amount]
    G --> H{Valid Amount?}
    H -- No --> I["Error: Min 2K / Max 2M / Over 16M"]
    H -- Yes --> J[applyTopup: balance += amount]
    J --> K[Save Write Journal as Backup]
    K --> L[Encrypt + Write NFC]
    L --> M{Verified?}
    M -- No --> N[Keep Journal → Retry on Next Tap]
    N --> B
    M -- Yes --> O[Delete Journal Entry]
    O --> P[Record Tx + Outbox]
    P --> Q[Success]

3. Check-in (Gate)

Aktor: Member (self-service kiosk di pintu masuk)
Tujuan: Mencatat masuknya anggota ke area koperasi dengan mengubah state kartu menjadi CHECKED_IN.
Alur: Kiosk berjalan dalam mode auto-scan terus-menerus → member tap kartu → sistem decrypt dan validasi (magic, HMAC, tenant bind) → cek tamper detection → cek status blokir (on-card + local DB) → validasi state machine: hanya kartu dengan state IDLE atau CHECKED_OUT yang bisa check-in → validasi saldo minimum Rp 10.000 (jaminan bisa bayar parkir nanti) → applyCheckin mengubah state, set session.startTime, increment counter → payload disimpan ke write journal sebagai backup → tulis ke kartu → jika verifikasi berhasil, journal dihapus, record transaksi dan trigger immediate sync push ke server. Jika verifikasi gagal, journal pending tetap ada dan akan di-retry otomatis pada tap berikutnya.
Write Journal (Retry Strategy): Sebelum write, payload disimpan ke journal sebagai backup. Jika verifikasi gagal, journal pending tetap ada. Pada tap berikutnya di gate yang sama, sistem mendeteksi journal → langsung retry write tanpa proses ulang. Setelah berhasil, journal dihapus.
Auto-reset: Setelah sukses/error, kiosk kembali ke mode scan otomatis untuk member berikutnya. 

flowchart LR
    A[Auto-Scan NFC] --> B{Pending Journal?}
    B -- Yes --> L
    B -- No --> C[Decrypt + Validate]
    C --> D{Tamper?}
    D -- Yes --> E[Reject: Invalid Card]
    D -- No --> F{Blocked?}
    F -- Yes --> G[Reject + Write Block]
    F -- No --> H{State == IDLE?}
    H -- No --> I["Reject: Already In / At Station"]
    H -- Yes --> J{Balance >= 10K?}
    J -- No --> K[Reject: Low Balance]
    J -- Yes --> K2[applyCheckin: state=CHECKED_IN]
    K2 --> K3[Save Write Journal as Backup]
    K3 --> L[Encrypt + Write NFC]
    L --> M{Verified?}
    M -- No --> N[Keep Journal → Retry on Next Tap]
    N --> P[Auto Reset]
    M -- Yes --> O[Delete Journal Entry]
    O --> O2[Record + Sync Push]
    O2 --> P[Success - Auto Reset]

4. Checkout (Terminal)

Aktor: Member (self-service kiosk di pintu keluar / terminal)
Tujuan: Mencatat keluarnya anggota, menghitung biaya parkir, dan mendebit saldo kartu.
Alur: Terminal berjalan dalam mode auto-scan → member tap kartu → decrypt dan validasi → cek blokir → validasi state: hanya CHECKED_IN atau STATION_OPERATION yang bisa checkout → hitung biaya: fee = ceil(durasi / 1 jam) × Rp 2.000 → validasi saldo cukup (balance - fee >= 0) → applyCheckout mendebit fee, set state CHECKED_OUT, catat session.endTime → payload disimpan ke write journal sebagai backup → tulis ke kartu → jika verifikasi berhasil, journal dihapus, record transaksi + sync → tampilkan durasi dan biaya yang dikenakan. Jika verifikasi gagal, journal pending tetap ada dan akan di-retry pada tap berikutnya.
Write Journal (Retry Strategy): Sebelum write, payload disimpan ke journal. Jika verifikasi gagal, journal pending tetap ada. Pada tap berikutnya di terminal, sistem mendeteksi journal → langsung retry write. Setelah berhasil terverifikasi, journal dihapus.
Insufficient balance: Jika saldo tidak cukup, member diminta top-up terlebih dahulu di station. 

flowchart LR
    A[Auto-Scan NFC] --> B{Pending Journal?}
    B -- Yes --> M
    B -- No --> C[Decrypt + Validate]
    C --> D{Tamper?}
    D -- Yes --> E[Reject: Invalid Card]
    D -- No --> F{Blocked?}
    F -- Yes --> G[Reject + Write Block]
    F -- No --> H{State == CHECKED_IN?}
    H -- No --> I["Reject: Not Checked In / Already Out"]
    H -- Yes --> J["Calculate Fee: ceil(hrs) x Rp2K"]
    J --> K{Balance - Fee >= 0?}
    K -- No --> L[Reject: Insufficient Balance]
    K -- Yes --> L2[applyCheckout: debit fee]
    L2 --> L3[Save Write Journal as Backup]
    L3 --> M[Encrypt + Write NFC]
    M --> N{Verified?}
    N -- No --> O[Keep Journal → Retry on Next Tap]
    O --> R[Auto Reset]
    N -- Yes --> P[Delete Journal Entry]
    P --> Q[Record Tx + Sync]
    Q --> R2[Success: Show Fee + Duration]

5. Scout (Read-only)

Aktor: Staff / Member (kiosk scout)
Tujuan: Membaca informasi kartu tanpa mengubah data apapun (read-only inspection).
Alur: Kiosk auto-scan → member/staff tap kartu → decrypt dan validasi payload → cek status blokir dari local DB → tampilkan informasi lengkap: nama anggota, status kartu, saldo (Rp formatted), Card ID (hex), jumlah transaksi (counter), dan riwayat 5 transaksi terakhir dari on-card log → jika kartu terblokir, tampilkan warning badge dengan alasan blokir → update local IndexedDB agar data terkini (balance, counter, status) tersinkron dari kartu fisik → auto-reset setelah 5 detik dan kembali ke mode scan.
Catatan: Operasi ini tidak menulis apapun ke kartu — murni pembacaan. Berguna untuk verifikasi dan troubleshooting. 

flowchart LR
    A[Auto-Scan NFC] --> B[Decrypt + Validate]
    B --> C{Valid?}
    C -- No --> D[Error: Retry]
    C -- Yes --> E[Check Blocked Status]
    E --> F{Blocked?}
    F -- Yes --> G[Show Warning Badge]
    F -- No --> H[Display OK]
    G --> I[Show Card Info]
    H --> I
    I --> J[Name / Balance / Status / Tx History]
    J --> K[Update Local DB]
    K --> L[Auto Reset 5s]
    L --> A
